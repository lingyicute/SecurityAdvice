# 写给高威胁模型下用户的安全与防御指南

**文 / lingyicute（梨）**

> **安全不始于系统安装完成的那一刻，而始于你决定信任什么。**

作为一名专注于个人计算安全的开发者和安全研究员，我经常与各种加固系统的开发者及安全极客们打交道。我很欣赏社区为打造更安全的操作系统（例如 secureblue 等项目）所付出的努力。但长期以来，大家的目光几乎总是被“漏洞利用缓解（Exploit Mitigation）”所局限——即如何提高内存破坏漏洞的利用成本、如何实施更严密的沙盒与虚拟化隔离、如何收紧进程权限等。

然而，安全遵循着极其严格的木桶效应。对于面临国家级攻击者、高度针对性的供应链攻击，或身处物理、人身胁迫风险中的高危用户（例如调查记者、人权活动家、掌握核心机密的研究人员，以及国家级 APT 组织的目标）而言，安全的核心痛点早已超越了“日常防挂马”，而是转移到了<strong>信任链（Chain of Trust）的完整性、国家意志的胁迫（State-sponsored Coercion）与针对性的供应链攻击（Supply-chain Attacks）</strong>上。

在这些极端对抗场景下，传统的“安全常识”不仅捉襟见肘，甚至可能产生致命的误导。我常常看到许多人忽视了一个最朴素、也最残酷的道理：

> **地基若已坍塌，其上筑造的城堡再巍峨，也终究不过是沙上之塔。**
>
> 正如 Qubes OS 的[安装安全性指南](https://doc.qubes-os.org/en/latest/user/downloading-installing-upgrading/install-security.html)所指出的：“如果你在一套已经失陷的硬件上安装操作系统，那么任何操作系统都帮不了你。”

因此，在这篇文章里，我想和你聊聊我心目中针对高威胁模型的核心安全理念：**真正的安全，绝不是孤立的系统加固，而是一条从物理世界、硬件、固件直到操作系统的完整、可验证的信任链。** 接下来，我将与你拆解这条信任链如何自底层逐级构建，并探讨在每一个关键环节上，高危用户应当践行的具体工程准则。

---

### 一、核心安全哲学：可审计性（Auditability）高于盲信缓解（Exploit Resistance）

安全社区中常有一种流行论调：“macOS 与 Windows 的漏洞缓解机制与历史工程投入显著优于多数开源 Linux 发行版，因此它们更安全。”

然而在我看来，如果非要说这种说法在哪种情况下能够勉强成立，那最多也就是对于普通商业用户而言了。且不论微软漫长的安全历史中事实上充斥着对设计缺陷的常态化妥协——其在官方策略中公开拒绝将 UAC 视为安全边界（Security Boundary），长期对大量 UAC 绕过漏洞视而不见，使得 Windows 的本地防线形同虚设；对于高威胁模型者而言，这种论调更是混淆了极其致命的概念：**难以被利用（Exploit Resistance）绝不等于系统本身可信（Trustworthiness）。**

许多人在讨论安全性时，经常将这两个概念混为一谈。**防利用性（Exploit Resistance）**指的是操作系统或软件在面对未知内存破坏等漏洞利用时的防御深度（如 ASLR、PAC、CET、MTE、CFI 等缓解机制），而**可信度（Trustworthiness）**则关乎**系统被植入特权后门、因法律或国家意志而被迫妥协，或在暗中被定向篡改的制度性与技术性可能**。

1. **国家胁迫与黑盒后门的风险**

   对于高危用户而言，**你的对手完全拥有合法或非法的权力，去胁迫私有软件厂商**。闭源商业系统（Windows/macOS）无论其安全缓解做得多么精妙，其本质依然是难以审计的“黑盒”。你几乎永远无法排除厂商在行政命令或情报机构秘密法令的胁迫下，被迫植入后门或特定过滤组件的可能。**请勿对闭源软件厂商在利益面前的底线抱有未经检验的温情幻想。**

   > *注：例如微软自 2024 年起通过 Windows 11 的预览版与累积更新（如 [KB5037858](https://winaero.com/windows-11-build-22635-3646-preinstalls-pc-manager-app-if-you-are-in-china/)），向“国家/地区”设置为中国大陆的设备静默安装不必要的不明附加软件，如“微软电脑管家”和 Office Plus 插件。微软还通过累积更新[静默下发过一个内核过滤驱动](https://kolbi.cz/blog/2024/04/03/userchoice-protection-driver-ucpd-sys/)。这类由厂商静默下发、无需用户确认的行为，在闭源生态中几乎处于审计盲区。
   
2. **“xz 事件”的本质启示：审计权与透明度优势**

   常有人以“Linux 生态同样爆发了 xz 供应链后门[（CVE-2024-3094）](https://nvd.nist.gov/vuln/detail/CVE-2024-3094)”为由，全盘否定开源方案的信任优势。然而事实的逻辑恰恰相反：**xz 后门之所以能够败露，正与代码和发行过程相对透明有关**——一名工程师（Andres Freund）注意到约 500 ms 的反常性能抖动后[顺藤摸瓜](https://www.openwall.com/lists/oss-security/2024/03/29/4)，最终发现了极为隐蔽的攻击代码。如果同等级别的隐蔽后门被植入到闭源的 Windows 或 macOS 内核深处，外部研究人员将完全丧失在源码层面快速审计与复现的能力。开源的价值从不在于“开放了源代码就可以自动自发地孕育出安全性”，而在于它保留了被独立审计的可能。闭源的问题也不是“一定有后门”，而是<strong>“即使有，你也没有资格发现”</strong>。对高危用户而言，安全决不能建立在“相信科技巨头的道德声誉”上，而是必须**将信任锚定在数学证明、开源审计与物理可验证性之上**。

### 二、终结“受污染宿主机”困境：构建绝对可信的介质制作环境

许多人在构建安全环境时，犯下的最大逻辑错误就是忽视了**安装介质生成的母体环境（The Compromised Host Problem）**。

如果你日常使用的 Windows 或 macOS 已经潜伏了恶意软件，无论你在其上如何验证 GPG 签名、如何使用刻录软件，恶意主机都可以轻易地在内存中伪造验证成功的提示，或在向 USB 写入 ISO 的最后一毫秒注入恶意 Payload（载荷）。

那么在高威胁模型下，如何安全地跨越这道鸿沟，完成新系统的“初次引导”呢？

1.  **将 Pixel + GrapheneOS 作为你的终极信任根（Root of Trust）**
    
    这是我极力推荐的方案，也是目前在消费级领域最具备可操作性、且密码学闭环的方案。搭载 GrapheneOS 的 Google Pixel 拥有当前消费级硬件中最强悍、且对用户透明的硬件信任根。当你的 Pixel 开机显示出那行独特的黄色 AVB 警告与验证启动公钥哈希时（Pixel 6 及以后的机型会显示完整 SHA-256，可与官方公布的哈希逐位比对），密码学逻辑确保了受 AVB 保护的系统镜像没有一行代码被非法篡改。利用 Pixel 的 USB-OTG 功能，配合开源无权限的写入工具（如 EtchDroid），将镜像写入 U 盘并回读验证（EtchDroid 自 2.0 起已内建写入后回读校验流程），这样在整个介质制作过程中，你就获得了一个完全干净、不可被主机篡改的离线环境。
    
    > **OPSEC（操作安全）小贴士：**
    >
    > AVB 能够抵御固件与系统级的篡改，但无法验证你手中的 Pixel 是否在出厂后被替换或植入了恶意硬件。为了防范针对性的硬件供应链劫持，高危用户应当尽可能穿着不引人注目的装束，在线下使用现金匿名购买 Pixel 设备。如果必须网购，那也绝对不要使用真实的身份信息，并避免把设备寄到受监控的地址。定向供应链攻击的成本，很多时候只有一个快递面单那么高。
    >
    > 另外，U 盘的选择同样至关重要：为了防范可能的针对性供应链攻击，我也建议你线下购买 U 盘。以同样低调的装束，随便走入一家超市——甚至最好是你平时不去的、地处偏僻的——并在货架上随机挑选未拆封的知名品牌 U 盘。不过，需要注意的是，随机购买只能降低“针对你个人”的定向劫持概率，并不能消除批次性或上游供应链污染。在当今这个供应链攻击难以察觉的时代，即使是原装塑封的新 U 盘，其主控固件也可能已被篡改。我建议你对该 U 盘进行受控的读写测试（例如在该 U 盘中写入 Live CD，插入一台试验电脑上启动，再拔下重新读取它进行检验），以试探其固件是否存在恶意行为。另外，**请勿购买“固态 U 盘（带复杂 SSD 主控）”或“指纹加密 U 盘”一类的产品**。此类产品不仅运行着极其复杂的闭源固件、拥有远比普通 U 盘更大的受攻击面与后门隐蔽空间，甚至其大肆吹嘘的“硬件加密”本身就可能是一场彻头彻尾的商业骗局（见下文第 4 节的联想 ThinkPlus 反面教材实录）。

2.  **物理防写介质的不可替代性**
    
    如果你必须使用传统 PC 制作或运行 Live 环境，请务必准备带有**物理只读拨动开关（Hardware Write-Protect Switch）**、且**固件不可更新、或至少对固件更新施加签名限制**的工业级 U 盘。这有助于从硬件层面降低恶意软件向系统映像回写恶意 Payload 的可能。
    
    > 为什么一定要强求固件不可更新、或至少带有签名限制？
    >
    > 因为将可重写固件的 U 盘插入已失陷的机器可能导致 [U 盘被入侵](https://web.archive.org/web/20160304013434/https://srlabs.de/badusb/)。被感染的 U 盘在工作时会动态向计算机注入恶意内容或模拟人机输入设备，瞬间摧毁你精心准备的全新安装环境。
    >
    > 为什么只是“有助于降低这种可能”，而不能杜绝？
    >
    > 因为只读开关是否真正由 U 盘主控在硬件层面强制执行，取决于具体实现。

3.  **打破对单一分发基础设施的信任（Out-of-band Verification）**
    
    只从官方网站下载公钥是危险的“单点失效”（Single Point of Failure）。如果网站基础设施或 CDN 遭到国家级入侵，攻击者完全可以同时替换 ISO 与公钥。高危用户必须掌握并践行[公钥指纹的带外交叉验证（Out-of-band Verification）](https://doc.qubes-os.org/en/latest/project-security/verifying-signatures.html#how-to-import-and-authenticate-the-qubes-master-signing-key)。

    这里是一些可供你参考的思路：
    
    *   在多个真正相互独立的平台上核对指纹（GitHub、Twitter/X、Bluesky、邮件列表、论坛、开发者个人社交媒体和博客等）；
    *   在非文本介质上寻找指纹印证（如会议演讲的 PDF、幻灯片、视频录像、甚至[官方发行的 T-shirt](https://x.com/legind/status/813847907858337793/photo/2) 上）；
    *   匿名在各大邮件列表与社区论坛公开征求第三方留存的历史指纹以供比对；
    *   从不同来源下载旧版 ISO，并检查 ISO 内随附的密钥文件；
    *   检查 Internet Archive 快照和 Git 历史里带签名的提交/标签。
    *   利用不同的网络环境（Tor 网络、各类 VPN 和代理服务，以及工作单位、学校、图书馆、网吧、不同 ISP 的公共 Wi-Fi 和蜂窝数据网络）重复请求上述数据；
    *   使用不同的设备进行交叉对比；
    *   如果可能，与社区成员或开发者进行线下会面或通过安全信道确认指纹。
    
    <br>
    
    > **OPSEC 小贴士：**
    > 
    > 以上建议很大程度上是海外视角。如果你身处中国大陆，那么你在家用宽带和蜂窝数据网络，以及工作单位、学校、网吧等实名场所的浏览活动很有可能是受到监控的。当你在不同的网络环境频繁密集地访问 GrapheneOS 或 Qubes 相关站点，这本身就可能构成情报。请务必谨慎。
    
    只有当所有独立渠道获取的指纹严丝合缝时，才能导入公钥进行验证。

4.  **绝对的反面教材：从联想 ThinkPlus“指纹加密”闹剧看商业“硬件安全”的破产**

    为什么我在上文中反复警告**绝不要碰商业“指纹加密 U 盘”与闭源“加密移动硬盘”**？如果说理论推演还不足以敲响警钟，那么安全研究员 Xusheng Li（Vector 35 核心开发者、Binary Ninja 调试器负责人）在 [RE//verse 2026 逆向工程大会](https://github.com/xusheng6/breaking_encrypted_USB_drives_with_TTD)上公开的一系列硬核拆解与逆向成果（参见 [HackingPassion 报道](https://hackingpassion.com/lenovo-thinkplus-encrypted-usb-sd-card/)及[后续研究](https://binary.ninja/2026/10/22/breaking-more-encrypted-usb-drives-with-ai.html)），就是商业“硬件加密”彻底破产的**绝对反面教材**：

    *   **荒诞剧第一幕：宣传 AES-256 硬件加密的联想 ThinkPlus FU100，拆开竟是一张明文裸奔的普通 SD 卡（CVE-2025-13453）**
        
        联想 ThinkPlus FU100 指纹 U 盘在商品页面大肆宣传采用“AES-256 硬件级加密技术”、“指纹/密码双认证”与“防数据泄露”。然而当研究员将其拆解后，塑料外壳底下的小电路板上**赫然插着一张最普通的标准 SD 存储卡——卡上的文件完全以明文（Plaintext）形式存储，零加密**。所谓的“指纹识别模块”，根本不参与任何密钥派生或数据加解密，它唯一的作用仅仅是充当一个**控制 USB 总线通断的电子开关**（决定 U 盘插入电脑时是否枚举挂载）。换言之，只要攻击者拿到物理设备、撬开外壳把里面的存储卡拔出来插进任何一个读卡器，所有“受 AES-256 保护”的机密文件就能直接读取。正如研究员在演讲中所言，它不过是<strong>“装在花哨外壳里的一张普通 SD 卡（just an SD card in a fancy case）”</strong>。
        
        更令人瞠目结舌的是厂商的第一反应：研究员于 2025 年 8 月 2 日向联想上报该漏洞后，厂商在 8 月 27 日拿出的所谓“临时修复方案”，竟然只是在内部 SD 卡上**糊上一层环氧树脂胶，掩盖它的存在**——**试图用一坨工业胶水来替代 AES-256 密码学计算**！

    *   **荒诞剧第二幕：联想 ThinkPlus TSD303 移动固态硬盘——把正确密码通过 USB 明文发回电脑做比对**
        
        在同一项研究中，研究员对联想 **ThinkPlus TSD303** 指纹加密移动固态硬盘进行了逆向分析。TSD303 内部使用的是标准 M.2 SSD，盘体数据虽然确实经过了加密，但其解锁验证协议却犯下了完全无法饶恕的低级工程错误：**当电脑端的联想配置管理软件请求验证密码时，硬盘竟然直接把正确的解锁密码以明文形式通过 USB 数据线发回宿主机电脑，交由上位机软件在内存中与用户输入的字符串做比对！** 在研究员捕获的 USB 数据包末尾字节中，正确的明文密码肉眼可读——任何能够嗅探 USB 流量或转储上位机进程内存的攻击者，都能直接拿走正确密码。
        
        联想在三个月后给出的第一版测试补丁更是“掩耳盗铃”：固件不再直接发回明文密码，而是改用 **SM4 分组密码**发送一段密文块（Blob）；然而研究员利用时间旅行调试（Time-Travel Debugging）逆向追踪发现，这段 SM4 密文的密钥竟然派生自一个形似时间戳的可预测数值（测试中直接还原出密钥 `2021012700000000`）。由于上位机程序本身就能推导出这把密钥，任何拆解客户端软件的攻击者同样能在几分钟内解密出正确密码。直到 2025 年 12 月的第二版固件更新，才终于将密码核验逻辑收回硬盘内部执行。

    *   **荒诞剧第三幕：一套公版 SDK 坑害 10 款设备，与联想高危公告 LEN-210545 的黑色幽默**
        
        这不是某一款单品的偶然失误，而是整个贴牌供应链的系统性腐烂。研究披露，与 TSD303 共用**同一套上游软件开发包（SDK）**的共有 **10 款加密存储设备**（除 TSD303 外还有**另外 9 款**来自不同品牌的同类设备）：其中 **6 款**直接通过 USB 明文发送密码交由电脑端比对，**2 款**直接在内部 microSD 卡上明文存放未加密数据，另外 **2 款**虽用 AES 加密传输密码但密钥完全可被还原。而在后续结合 Binary Ninja MCP 与 AI（OpenAI Codex）的自动化逆向中，研究员仅用 7 到 26 分钟便陆续击穿了朗科（Netac `NetacFileLock（部分文档亦作 NetacLockFile）`，将 32 字节 AES-256 密钥硬编码在程序中，且快速模式下每 48 字节仅加密 16 字节、其余 32 字节明文裸奔）、御天盾（SecZure YutianDun，暗藏密码为 `123456` 的 `Buffer` 隐藏账户与密码为 `SECZURE.COM` 的 `System` 内置后门账户）、KakaSoft 与 Nexcopy 等多款商业加密/防拷贝 U 盘。
        
        2026 年 1 月 13 日，联想正式发布**高危级别（High Severity）安全公告 [LEN-210545](https://iknow.lenovo.com.cn/detail/436983)**，确认波及 **ThinkPlus FU100、FU200、TU800** 指纹 U 盘及 **TSD303** 移动固态硬盘，并分配了三个 CVE 编号：
        
        *   **[CVE-2025-13453](https://nvd.nist.gov/vuln/detail/CVE-2025-13453)**（CWE-311 缺失敏感数据加密）：具备物理接触权限的攻击者可直接读取部分 ThinkPlus U 盘上存储的数据；
        *   **[CVE-2025-13454](https://nvd.nist.gov/vuln/detail/CVE-2025-13454)**：ThinkPlus 配置软件允许本地已登录用户获取敏感设备信息；
        *   **[CVE-2025-13455](https://nvd.nist.gov/vuln/detail/CVE-2025-13455)**（CVSS 3.1 评分 **7.8 高危**，CWE-290 欺骗绕过认证）：ThinkPlus 配置软件允许本地已登录用户绕过设备身份验证，直接录入不受信任的指纹。
        
        更具讽刺意味的是其补救方式：由于缺陷深植于硬件架构与底层固件，联想无法提供在线自助更新，只能要求用户拨打中国区服务热线**寄回换货或安排现场固件升级**，并在公告中写道“寄送前请先备份并彻底删除或格式化数据”——对于一个不幸轻信了“AES-256 硬件加密”宣传的高危用户而言，他不仅放任了自己的敏感数据自始至终在普通 SD 卡上明文裸奔，最后甚至还要把存过机密的介质亲手寄回给厂商 —— 而 NAND 闪存颗粒的磨损均衡机制导致其残留的明文数据很难彻底擦除。

    > **从反面教材提炼的硬核防御铁律：**
    > 
    > 1. **切勿混淆“访问门禁（Access Gate）”与“密码学加密（Cryptographic Encryption）”**：外壳上的指纹传感器、或者插上电脑弹出的密码输入框，往往只是一道控制 USB 枚举或软件界面的“门禁”。如果底层闪存扇区没有使用由高熵密钥加密，拆壳读卡或逆向客户端就能直接绕过门禁。
    > 
    > 2. **客户端校验（Client-side Validation）永远等同于不设防**：任何把密码或密钥传回宿主机内存做比对、或将固定密钥/可预测种子硬编码在闭源客户端里的设计，在调试器与逆向面前都撑不过十分钟。
    > 
    > 3. **把密码学主权握在自己手中**：永远只把 U 盘当成完全不可信的裸块设备（Raw Block Device），在可信开源操作系统上使用经过全球密码学界千锤百炼的开源工具自行加密——如 Linux 原生的 **LUKS2（`cryptsetup`，默认采用抗暴力破解的 Argon2id 密钥派生函数）**、跨平台的 **VeraCrypt**，或单文件级的 **GnuPG（`gpg --symmetric --cipher-algo AES256`）**。只有当加密密钥完全由你的高熵口令经慢速 KDF 派生，且密文在写入 USB 总线之前就已经在你的受控主机内存中完成加密时，即便攻击者拆出 U 盘里的存储卡乃至直接用编程器读取 NAND 闪存颗粒，拿到的也只是一堆在数学上无法与随机噪声区分的密文。

### 三、固件深渊：UEFI 泡沫、SMM 幽灵与真实防御

当 OS 级别的加固（如强化内核、强制访问控制、无特权设计）变得足够坚固，到了正面攻破它的成本已经高于绕过它的成本的程度，理性的攻击者绝不会继续硬啃。他们会向上、向下、向外移动，例如：降维到你的**固件与硬件**。

#### 1. 警惕商业 OEM 的安全营销与供应商原罪
有些观点认为只需要购买主流品牌的商用笔记本即可，但我必须对此提出严厉的质疑。这是一种危险的怠惰。

评估硬件可信边界的基石，是供应商的历史履约行为。例如，[某些知名 PC 厂商曾有劣迹斑斑、屡教不改的历史记录](https://www.theregister.com/software/2015/08/12/caught-lenovo-crams-unremovable-crapware-into-windows-laptops-by-hiding-it-in-the-bios/584105)：其曾利用 UEFI 的 WPBT（Windows Platform Binary Table）机制，在固件层强行向操作系统的引导流程中注入间谍软件与垃圾程序，甚至替换系统文件。而在十年后的今天，恰恰又是同一家厂商，在其 ThinkPlus 存储产品线上演了上文详述的**虚假加密丑闻**——把内部塞着未加密普通 SD 卡的 U 盘包装成“AES-256 硬件加密”售卖，被拆解戳穿后甚至一度企图用环氧树脂把 SD 卡糊住来充当“临时修复”；其 TSD303 移动固态硬盘更是直接通过 USB 明文回传正确密码。从 2015 年滥用 UEFI WPBT 机制驻留 BIOS 后门，到 2025–2026 年用普通明文 SD 卡和胶水糊弄信任其“硬件加密”承诺的用户，血淋淋的事实一再证明：
一个在和平时期，仅仅为了商业利益或工程偷懒便主动践踏固件与 OS 边界、把“硬件安全”当成纯粹营销话术的厂商，没有任何资格进入高威胁模型的选型清单。在商用硬件选择上，不应只看品牌，而应核查其固件更新记录、安全响应历史，以及企业级产品线是否接受过持续的外部安全评估。只有经过充分安全设计与持续审计的厂商才勉强算是合格的起点。

#### 2. UEFI 的结构性溃烂与 SMM（Ring -2）的系统性危机
商用硬件声称的“安全启动”与“Intel Boot Guard”，在面对高级攻击时往往不堪一击。近年来诸如 [LogoFAIL](https://www.binarly.io/blog/far-reaching-consequences-of-logofail)、PKfail 等系统性灾难，已经彻底戳破了专有 UEFI 的安全性泡沫——数百万行晦暗不明的闭源 C 代码、脆弱内嵌的各种格式图像解析库，甚至还有完整集成的网络协议栈。[PKfail（CVE-2024-8105 / BRLY-2024-005）](https://www.binarly.io/advisories/brly-2024-005)更是暴露了供应链管理的形同虚设：大量主流 OEM 厂商在长达十余年的时间里，于量产设备中直接沿用上游独立 BIOS 供应商（IBV）提供的测试平台密钥——其证书 CN 干脆写着 “DO NOT TRUST – AMI Test PK”，且其中一把私钥早已随 ODM 源码泄露出现在公开仓库，使得 Secure Boot 瞬间沦为防君子不防小人的空壳。

更为致命的是 **SMM（系统管理模式）漏洞**。SMM 的执行权限凌驾于操作系统内核乃至 Hypervisor 之上（位列 Ring -2 级别）。商业 UEFI 内部充斥着极其臃肿且无法审计的 SMI 处理程序。攻击者一旦利用操作系统浅层提权链击穿 SMM，便可绕过所有系统防御，直击主板 SPI Flash，植入无法被侦测、无法随系统重装清除的持久化 Rootkit。

更具讽刺意味的是，Intel Boot Guard 的架构在面对此类攻击时存在天然局限：它在硬件上仅保证了初始引导块（IBB）各 hashed segments（哈希段）的签名完整性。且不说大量 OEM 在出厂时错误地将 Boot Guard 策略配置为“仅度量而不阻断引导”的宽松模式，或把“校验失败后的处置策略”错误地配置为宽松模式——校验失败时仅告警并继续引导，而不是直接关断平台（fwupd 的 HSI 检查正为此设了专门项）——即使配置正确，Boot Guard 在完成 IBB 校验并将控制权移交给后续体量庞大的 DXE 驱动卷执行阶段后，其硬件信任锚点便已告一段落，后续阶段庞大 DXE 驱动卷的校验工作即全面脱离了硬件锚点，完全仰赖各厂商自行编写、漏洞频出的私有 UEFI 验证逻辑。

#### 3. 为什么走向开源固件（coreboot / Heads）不是退步，而是必然
有人或许会误认为，将功能丰富的厂商 UEFI 替换为简陋的开源固件是一种“倒退”。这种看法完全忽略了固件攻防的本质：
*   **极致削减攻击面**：coreboot 和 Heads 剥离了几乎所有的冗余代码，并将 SMI 处理程序精简到了极限。**只要固件层没有可利用的 SMM 漏洞，且 SPI 写保护等配置已正确置位并锁定，操作系统级别的攻击者就丧失了向 SPI 芯片写入恶意代码的特权跳板。**
*   **度量启动（Measured Boot）与物理防篡改（Physical OPSEC）**：Heads 将固件各组件与启动链的度量值扩展到 TPM 的 PCR（主要是 PCR 2）中，并可通过 USB 安全密钥（如 Nitrokey）的 HOTP 验证和手机上的 TOTP 验证码让用户直观核对。配合物理防御手段（如将 SPI WP# 引脚物理接地，并正确置位、锁定状态寄存器中的写保护位，再在机身固定螺丝上使用混入随机彩色闪粉的指甲油制作简易的防拆封印并拍照留底），这为抵御“邪恶女佣攻击（Evil Maid Attack）”提供了严密的物理与密码学闭环。

    > 关于 Heads 的常见误区
    > 
    > Heads 并非无懈可击。[技术上讲](https://github.com/linuxboot/heads/blob/master/doc/architecture.md)，位于 reset vector、硬件复位后最先执行的 coreboot bootblock 充当 S-CRTM（Static Core Root of Trust for Measurement），计算 FMAP 与自身映像的哈希作为首批度量并记入 preram 事件日志；待 ramstage 初始化 TPM 后 extend（拓展）进 PCR 2，随后 romstage、ramstage 以及 Heads 的 Linux payload 同样以逐级传递的方式由前一级先行度量、逐级累积进 PCR 2。理论上，如果国家级攻击者拥有物理接触的机会，并伪造了一个 bootblock 向 TPM 发送虚假的度量值，它依然可以诱使 TPM 解封 TOTP/HOTP 共享秘密，从而显示看似正常的验证码。
    >
    > 然而，只要确保 bootblock 未被物理篡改，Heads 就是当前极其优秀的验证启动实现——它会对 /boot、内核、initrd、GRUB 配置实施严格的密码学验证。
    >
    > 因此，我们需要用“物理防拆手段”来填补这最后一块拼图。Heads 革命性的架构价值恰恰在于此：**它把过去“必须物理保护整台计算机每一个部件”的近乎苛刻的要求，压缩到了“只需物理保护主板上一颗小芯片中一块永远不变的区域”**，而将其余所有的信任链全部交由密码学来验证。这才是让“物理保护”在工程实践中第一次变得切实可行的东西。

#### 4. 理性审视 Intel ME（Ring -3）：隐式信任边界与攻击面收敛
我们一路向下，从操作系统追到了 UEFI 与 SMM（Ring -2）。但如果你以为 SMM 就是这条链的尽头，那就太乐观了。在 Intel 平台上，<strong>还有一层比 SMM 更深、更不透明、也更难摆脱的东西，在你按下电源键之前，它就已经醒着了。</strong>它就是 <strong>Intel ME（Management Engine，现称 CSME，Converged Security and Management Engine）</strong>—— 一个集成在芯片组（PCH）中的独立协处理器（部分近年平台则集成在 SoC 内）。自 2006 年起，它便几乎成为了 Intel 平台的标配。它是 Intel AMT、Intel Boot Guard、PAVP、固件 TPM（PTT）等一系列“安全与管理特性”的硬件基础。为了提供这些特性，它必须拥有近乎<strong>完整的系统访问权限</strong>：

*   **自带 CPU、自带操作系统：** 最早的版本基于 ARCompact 架构。自第 6 代酷睿 Skylake / ME 11 起换装为 32 位 x86 架构的 Intel Quark 核心。其操作系统最初基于 ThreadX，后来跑的是[经过 Intel 修改的 MINIX](https://www.theregister.com/2017/11/20/intel_flags_firmware_flaws)；
*   **先于主 CPU 启动，并且常驻：** 它负责平台初始化、电源管理，乃至于启动主处理器本身。只要主板通电，哪怕整机处于“关机”状态，ME 也可能仍在运行（[Black Hat EU 2017 的议题标题就叫《如何入侵一台已关机的电脑》](https://blackhat.com/docs/eu-17/materials/eu-17-Goryachy-How-To-Hack-A-Turned-Off-Computer-Or-Running-Unsigned-Code-In-Intel-Management-Engine.pdf)）。
*   **能直接读写你的内存，也能触碰你的网络：** ME 可通过 DMA 访问主机内存；在支持 vPro/AMT 的机型上，它还带有内建的 Web 服务与 VNC 服务，通过 WSMAN 协议暴露近乎完整的平台控制权，其带外网络功能依赖主板上与芯片组直连的 Intel 网卡。在已配置 AMT 的场景下，相关流量可以在到达操作系统网络栈**之前**就被 ME 截获——这意味着你在操作系统里配置的任何软件防火墙都完全看不到它。
*   **无法移除，也无法替换：** 从 Nehalem（ME 6）开始，ME 固件就[不能再被整体删除](https://github.com/corna/me_cleaner#what-can-be-done)：没有有效的 ME 固件，机器会在约 30 分钟后被强制关机。它的代码由 Intel 签名，因此无法替换或重新实现；在相当长的时间里，其模块还以未公开的霍夫曼码表压缩，直到 2017 年才被 Positive Technologies 的研究员[逆向还原](https://www.ptsecurity.com/ww-en/analytics/disabling-intel-me-11-via-undocumented-mode/)。

然而，这一节无意渲染恐慌。**截至本文撰写之时，没有任何公开证据表明 Intel ME 中存在被蓄意植入的后门**，Intel 也[公开否认过](https://www.zdnet.com/article/researchers-say-intels-management-engine-feature-can-be-switched-off/)这种说法。在安全社区的讨论中，Intel ME 常被过度渲染为某种令人谈虎色变的“终极全能后门”，甚至由此衍生出一种宿命论式的技术虚无主义 —— 认为只要使用的是现代 Intel 处理器，一切固件加固与操作系统隔离都毫无意义。但在我看来，这种过于骇人听闻的叙事偏离了客观的工程事实，也模糊了威胁建模中至关重要的**信任边界**。

回到信任链的第一性原理，我们首先需要坦诚面对一个基本前提：**当我们使用 Intel CPU 时，其实本就不得不在一定程度上隐式地信任 Intel。** 从硅片级的微架构逻辑电路、微码（Microcode）及其更新机制、硬件随机数生成器（RDRAND/RDSEED）、内存控制器，到后文借以实现硬件强隔离的 VT-x 与 VT-d（IOMMU），整个计算底座的物理执行均建立在芯片原厂的设计与制造之上。如果在威胁模型中先验地假设芯片原厂已经在硅片硬件层面对用户发起了背叛，那么在单机范畴内讨论任何软件或固件防御都将失去支点。

回到正题，既然我们已经隐式地信任了 Intel 的硅片设计，为什么在工程实践中依然需要对 Intel ME 保持警惕并加以限制？答案并不在于捕风捉影的阴谋论，而在于**收敛高特权伴生系统的受攻击面（Attack Surface）**：

*   **隐式信任硅片硬件，不等于无条件放任庞大的闭源伴生系统全功能运行**：Intel ME 本质上是一套集成在芯片组/SoC 内部、独立于主 CPU 核心运行的微型专有操作系统，拥有独立访问系统内存（DMA）与部分总线的极高权限（Ring -3）。我听到过有人试图用“Intel 工程实力雄厚，底层固件不会出低级错误”来为 ME 洗地，然而任何足够复杂的软件系统都不可避免地存在实现缺陷——历史上的多项高危安全公告（例如著名的 [INTEL-SA-00086](https://www.intel.com/content/www/us/en/security-center/advisory/intel-sa-00086.html)、[CVE-2017-5689](https://nvd.nist.gov/vuln/detail/CVE-2017-5689) / [CVE-2017-5705](https://nvd.nist.gov/vuln/detail/cve-2017-5705) 等栈缓冲区溢出与任意代码执行漏洞）早已表明了 ME 固件的代码质量不佳。这些代码缺陷一旦被攻击者利用，就会沦为可完全绕过主操作系统防线的持久化跳板，而国家级攻击者完全有能力实施此类攻击。因此，我们对 ME 采取限制措施的逻辑，与前文剥离臃肿 UEFI、精简 SMM 完全一脉相承：为了**遵循最小权限与最小攻击面原则，杜绝高危冗余代码运行。**
*   **坚决规避并禁用 Intel AMT / vPro（主动管理技术）**：在威胁评估中，必须严格区分普通消费级 ME 固件与支持企业级 **vPro / AMT（Active Management Technology）** 的固件。AMT 的设计初衷是为大型企业提供带外（Out-of-Band）远程运维能力——即便主操作系统处于关机、崩溃或防火墙严密封锁的状态，AMT 依然能够通过独立的网络协议栈响应远程指令（甚至接管 KVM 画面与挂载远程镜像），且历史上曾曝出过极其严重的远程认证绕过漏洞（如 [INTEL-SA-00075 / CVE-2017-5689](https://nvd.nist.gov/vuln/detail/CVE-2017-5689)）。对于高危个人用户而言，企业级带外远程管理纯粹是高风险负资产。在硬件选型时应优先选择非 vPro 版本的处理器与主板，或在固件及 ME 配置（MEBx）中彻底关闭 AMT 及相关网络唤醒功能。
*   **利用 HAP 位或 `me_cleaner` 实施“早退与去功能化（Neutralization）”**：在现代 Intel 架构下，你无法简单地将 SPI Flash 中的 ME 区域彻底抹除——因为硬件上电时序要求 ME 必须参与早期芯片组初始化与主 CPU 唤醒（BUP，Bring Up）；若完全缺失 ME 固件，主 CPU 将无法启动，或在运行约 30 分钟后被硬件看门狗强制断电。因此，最务实的工程方案是让 ME<strong>“完成上电初始化后即刻退场”</strong>：
    1.  **置位 HAP（High Assurance Platform）位（或早期平台的 `AltMeDisable` 位）**：这是 Intel 在固件配置中预留的官方高保障模式开关。启用后，ME 仅执行启动主处理器所必需的早期初始化逻辑（BUP 阶段），随后便主动进入禁用/挂起状态，不再加载后续庞大的运行时模块。目前主流的开源固件生态（如 [coreboot](https://doc.coreboot.org/)、[Dasharo](https://docs.dasharo.com/) 以及预装开源固件的 NovaCustom、Star Labs、System76 等机型）均可配合被 HAP 禁用的 ME 使用。
    2.  **结合 [`me_cleaner`](https://github.com/corna/me_cleaner) 裁切冗余模块（针对受支持代系）**：在刷写 coreboot / Heads 的经典机型（如 ThinkPad X230、T480 等）上，除置位禁用标志外，还可配合 `me_cleaner` 直接移除除 `rbe`、`kernel`、`syslib`、`bup` 等核心启动分区之外的绝大部分运行时模块。
*   **保持固件更新，并定期自检**：通过 OEM 与 LVFS 获取 ME / CSME 的更新，并使用 `fwupdmgr security` 查看 HSI 报告，关注 ME 版本与 Manufacturing Mode 相关项。注意：ME 更新通常由 OEM 通过 BIOS 更新分发，停止维护的旧机型意味着不再有补丁。

    > *注：切勿对 AMD 平台抱有盲目的“避风港幻想”。
    >
    > 许多人在了解到 Intel ME 后，第一反应往往是：“那我彻底抛弃 Intel，直接去买一台普通的商用 AMD 笔记本不就安全了吗？”这同样是一种危险的幻觉。自 2013 年起，AMD 也在其芯片组与处理器内部塞入了一颗地位完全对等的 Ring -3 黑盒协处理器——**AMD PSP（Platform Security Processor，后被 AMD 改头换面包装为听起来更无害的 AMD Secure Processor）**。它本质上是一颗独立运行专有闭源固件的 ARM TrustZone（Cortex-A5）核心，同样凌驾于主 x86 CPU 之上并掌握着全系统物理内存的最高访问权，历史上同样爆发过严重的栈溢出与特权泄露漏洞（如 [CVE-2019-9836](https://nvd.nist.gov/vuln/detail/CVE-2019-9836)、[CVE-2021-26333](https://nvd.nist.gov/vuln/detail/CVE-2021-26333)），且开源社区针对 AMD PSP 的固件剥离能力与工具成熟度甚至远不及 Intel 平台的 `me_cleaner`。在当下由双寡头垄断的现代 x86 硅片世界里，早已没有天然无瑕的世外桃源。我个人非常期待 RISCV 等自由架构带给我们更多的选择。

### 四、防御不仅是理论，更是严谨且可落地的交互（UX）

最后，我想聊聊我们作为开发者和安全研究人员，应该如何看待“安全防线的设计”。

高深的安全理论如果不具备可操作性，便只是象牙塔里的自娱自乐。以 **IOMMU（VT-d / AMD-Vi）** 为例：
像 secureblue 这样的默认加固系统，会在内核启动参数中[启用并强化 IOMMU 相关设置](https://secureblue.dev/articles/kargs)，旨在防御来自无线网卡等不可信硬件，以及外接 Thunderbolt、PCIe 设备的 DMA 攻击。

然而现实是：**许多主板在出厂时，BIOS/UEFI 里的 IOMMU 开关默认是关闭的。**
如果操作系统在安装时保持沉默，用户就完全无从知晓这层保护并未激活。即使内核参数写得再漂亮，只要硬件寄存器未被激活，防线便形同虚设。一旦有恶意硬件插入，系统依然会沦陷。

这绝非什么“用户无法改变”的硅缺陷——用户往往只需要按下 Del/F2 键步入固件设置，将那个关键的选项切换为“Enabled”。因此，**加固系统必须在安装阶段主动探测相关状态，并向用户展示清晰的警示与引导。这是让抽象安全理论穿透硬件迷雾、真正兑现为防御能力的最后一块拼图。**

### 结语

在与高等级威胁漫长、孤寂且充满压迫感的博弈中，我们往往极易陷入压抑、怀疑、技术虚无甚至宿命论的泥潭：面对掌握着近乎无限资源的庞大对手，个体竭尽全力的防御是否注定是一场徒劳？

我的答案始终是否定的。

安全不是非黑即白的玄学，它是一门关于**风险管理、攻击成本提升与信任链条闭合**的精密科学。当我们拒绝盲从大厂的黑盒承诺，当我们学会在物理隔离的纯净环境中完成第一次验证，当我们认真审视固件的每一行代码与主板上的每一个开关——我们就已经从无形的信息迷雾中突围，将关乎自由与安全的主动权，重新夺回到了自己手中。

愿我们在充满未知的技术荒原上，始终怀揣冷静的审视、严密的逻辑，以及对自己所守护之物的温柔与坚定。
